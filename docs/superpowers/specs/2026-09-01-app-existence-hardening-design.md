# App Existence Hardening Design

**Status:** OWNER-AUTHORIZED TEST-PHASE PRODUCTION-GRADE FOUNDATION

## Purpose

Raise LIGHTHOUSE app-existence foundations to production-grade standards while the product is still in test. Test phase is the proving ground for permanent contracts, not an excuse for temporary security, lifecycle, recovery, or native-platform shortcuts.

## Scope

This design covers only four incomplete roots discovered by Reality Refinery:

1. Lifecycle and durable-state survival evidence.
2. Backup and recovery secret boundary plus end-to-end recovery proof.
3. Generated Android native security baseline.
4. Physical-device evidence gates that complete APK identity continuity without bypassing PR #96.

App/package identity, canonical APK signer custody, monotonic Android versioning, final-byte APK identity verification, and signed Patch trust remain owned by the existing APK identity continuity work and are not redesigned here.

## Global Invariants

- Reality evidence outranks documentation or intended behavior.
- Production-grade contracts apply now even though product capability is still under test.
- No simulated CI result may be labeled as physical-device proof.
- No product capability expansion is part of this work.
- No production deployment or store publication is part of this work.
- Existing Greenfield/Manual business semantics and Patch trust semantics remain unchanged.
- Security hardening must preserve recoverability of legitimate legacy backups.

## Backup / Recovery Boundary

### New backup rule

A current-format portable backup must never carry a plaintext usable recovery secret in the same envelope as the encrypted vault payload. Possession of a backup file alone must not be sufficient to decrypt business data.

### Recovery key custody

Recovery material is supplied separately at restore time through an owner-controlled recovery path. The backup envelope may contain only non-secret metadata required to identify format/version and encrypted vault content.

### Legacy compatibility

Existing backups that already contain `recoveryKey` remain readable through an explicit legacy compatibility path. Legacy embedded-key backups must be detected and reported as legacy; new exports must not produce that format.

### Recovery acceptance

A backup path is accepted only when it proves: export from durable state, destructive loss/reset or empty target, restore with separately supplied recovery material, durable readback equality, corrupt/wrong-key fail-closed behavior, and preservation of an existing target when replacement is not explicitly authorized.

## Lifecycle / Durable State

Automated tests may prove browser-store reopen semantics, session closure behavior, stale pending-command rejection, encrypted durable readback, and state reconstruction from IndexedDB.

Physical-device proof is still required for force-stop/process death/device reboot and post-APK-upgrade continuity. These states must remain VERIFY until hardware evidence exists.

No test may substitute an in-memory store for a claim about Android process death or device reboot.

## Native Android Security Baseline

Because the Android project is generated by Capacitor in CI, security is verified from generated native reality after `cap sync android`, not inferred from web configuration.

A fail-closed verifier must inspect the generated/merged Android configuration and record evidence for at least:

- application/package identity
- requested permissions
- exported activities/services/receivers/providers
- backup policy (`allowBackup`, data extraction/backup rules when applicable)
- cleartext/network-security policy
- debuggable/release posture where observable
- WebView/native bridge surface relevant to enabled Capacitor plugins

The verifier must run before signing/publication of the canonical APK and produce a non-secret evidence artifact. An unknown security-sensitive field is VERIFY/BLOCKED, never PASS-by-absence.

## Physical Device Gates

PR #96 Phase 6.2 remains authoritative. Canonical APK B must not be produced until APK A is established on real hardware with known durable Greenfield/Manual state, Patch state, and enrollment/unlock state, followed by close/reopen readback.

After APK A -> B in-place update, the same state must survive without uninstall or storage clear. Lifecycle device checks and backup/recovery device checks may share the same controlled hardware session where doing so does not weaken evidence boundaries.

## Exit Criteria

This hardening work is complete only when:

- new backups no longer embed usable plaintext recovery material;
- legacy backup compatibility is retained explicitly and tested;
- generated Android security configuration is fail-closed verified in CI from native reality;
- lifecycle/storage automated contracts cover all claims automation can honestly prove;
- physical-only lifecycle/reboot/upgrade/recovery claims remain gated until actual hardware evidence exists;
- all evidence is recorded as PROVEN / VERIFY / BLOCKED without architecture or capability expansion.
