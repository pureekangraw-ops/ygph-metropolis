# YGPH AI + Manual Foundation Design

Status: DESIGN APPROVED / WRITTEN SPEC FOR REVIEW
Date: 2026-08-27

## 1. เป้าหมาย

ทำให้ YGPH กลับมาเป็น **Yggdrasil Personal Helper** แบบที่ชื่อเดิมตั้งใจไว้:

คนพูดกับ AI → AI ตีความ → **เกทส่งออกของ AI** ใช้วุ้นแปลภาษาแปลงให้เป็นภาษาแอปมาตรฐาน → **เกทรับเข้าของ Manual** รับภาษาแอปและกระจายไปยังพื้นที่ที่ถูก → logic ของแอปทำงาน → แสดงผลให้คนตรวจได้

รอบนี้ไม่พยายามทำทุกอย่างให้ครบก่อน เป้าคือวางฐานที่ถูกตำแหน่ง โตต่อได้ และพิสูจน์เส้นทางง่ายหนึ่งเส้นให้ผ่านจริง

## 2. หลักที่ใช้ตัดสินใจ

- เริ่มจาก Reality ของการใช้งาน ไม่เริ่มจากโครงเดิมว่าต้องรักษาอะไร
- ของเดิมที่ช่วยโครงใหม่จริง ใช้ต่อ
- ของเดิมที่ทำให้ต้องอ้อม ซ้ำ หรือบวม ตัดหรือแทนได้
- ของที่ “ดี” แต่ไม่เหมาะกับงานนี้ ไม่จำเป็นต้องเพิ่ม
- Safety ต้องเป็นราวกันตก ไม่ใช่กำแพงขวาง flow
- ความครบไม่ใช่เป้าหมายของรอบฐาน
- Logic งานจริงยังอยู่ในฝั่ง Application / Manual ไม่ย้ายไปฝากไว้กับ AI, เกทส่งออก หรือเกทรับเข้า

## 3. Working Shape ของแอป

### A. หน้า AI — สร้างใหม่

หน้าที่หลัก:

`คำพูด → ตีความ → ส่งความหมายออก`

หน้า AI เป็น chat-first

AI ต้องทำให้ชัด 3 จุด:

1. รับอะไรเข้ามา
2. เข้าใจว่าอะไร
3. กำลังส่งความหมายอะไรออกไป

AI ไม่ต้องรู้รายละเอียดว่าภายใน Manual จะจัด logic กันอย่างไร

### B. เกทส่งออกของ AI — มีวุ้นแปลภาษาอยู่ข้างใน

หน้าที่หลัก:

`ความหมายจาก AI → วุ้นแปลภาษา → ภาษาแอปมาตรฐาน → ส่งออก`

วุ้นแปลภาษาทำหน้าที่เป็น **Dictionary + Normalizer + Validator แบบเล็ก** ภายในเกทส่งออก

ตัวอย่างสิ่งที่แปล:

- `expense / รายจ่าย / outcome` → `OUTCOME`
- `65 บาท` → `6500 satang`
- ชื่อ field ต่างกัน → ชื่อ field มาตรฐานของแอป
- วันที่ / เวลา → รูปแบบมาตรฐานเดียวกัน

เกทส่งออกต้องปล่อยออกเฉพาะภาษาแอปที่อยู่ในรูปที่รับรองแล้วสำหรับรอบนั้น

ข้อกันหลุด:

- ไม่มี state ธุรกิจของตัวเอง
- ไม่อ่านหรือเขียนข้อมูลธุรกิจ
- ไม่ตัดสินว่า logic ภายใน Manual ต้องทำอะไรต่อ
- ไม่เรียก Ledger / Calendar / business workflow เอง
- ถ้าแปลไม่ได้หรือเจอคำที่ไม่มีใน contract ให้หยุดและส่งกลับว่าไม่รู้ ไม่เดาเอง

จุดประสงค์คือทำให้ AI ส่งออกเป็นภาษาของแอปที่ชัดและสม่ำเสมอ โดยไม่สร้างสมองก้อนใหม่

### C. เกทรับเข้าของ Manual — มีตัวกระจายงานอยู่ข้างใน

หน้าที่หลัก:

`ภาษาแอปมาตรฐาน → ตรวจรับ → อ่าน target → กระจายไปยังพื้นที่ Manual ที่ถูก`

ตัวกระจายงานเป็นจุดส่งต่อของ Manual และอยู่ **ภายในเกทรับเข้า** ไม่ได้เป็นวงจร business logic ของ Manual

เกทรับเข้าทำเพียง:

- รับภาษาแอปมาตรฐาน
- ตรวจว่ารูปแบบพื้นฐานที่ Manual รับได้ยังถูกต้อง
- ดู `target`
- ส่งก้อนงานไปยังจุดรับของ INCOME / OUTCOME / LEDGER / CALENDAR หรือพื้นที่ที่เพิ่มในอนาคต
- ถ้า target ไม่รู้จักหรือข้อมูลรับเข้าไม่ผ่าน ให้หยุดที่เกท ไม่ปล่อยเข้าวงจรภายใน

เกทรับเข้า **ไม่ทำ business logic แทนพื้นที่ปลายทาง** และไม่วิ่งอยู่ในวงจรการคุยกันภายใน Manual

### D. หน้า Manual — ลดของเดิมให้เหลือฐาน

หน้าที่หลัก:

`รับงานจากเกทรับเข้า → เข้าโซน → logic วิ่ง → แสดงผล / audit`

พื้นที่ฐานชุดแรก:

- INCOME
- OUTCOME
- LEDGER
- CALENDAR

พื้นที่เหล่านี้ต้องเพิ่มหรือลดได้ในอนาคต โดยไม่ต้องรื้อทั้งหน้า

Manual ไม่ใช่จอแสดงผลของ AI และไม่ใช่ fallback

ต่อให้ไม่มี AI ผู้ใช้ยังต้องเข้ามาทำงาน ตรวจ และควบคุม logic ของแอปจาก Manual ได้

หลังงานผ่านเกทรับเข้าและเข้าพื้นที่ปลายทางแล้ว วงจรภายใน Manual จึงค่อยทำงานร่วมกันเองตาม logic จริง เช่น OUTCOME อาจสัมพันธ์กับ LEDGER หรือ CALENDAR โดยไม่ย้อนกลับไปใช้ตัวกระจายงานเป็นผู้จัดการวงจร

## 4. ภาษาแอป — Foundation Contract

รอบฐานใช้ contract เล็กที่สุดที่พิสูจน์ flow ได้

ตัวอย่าง:

```json
{
  "version": "1",
  "action": "CREATE",
  "target": "OUTCOME",
  "fields": {
    "title": "ข้าว",
    "amountSatang": 6500
  }
}
```

ความหมาย:

- `version` = รุ่นของภาษาแอป
- `action` = ต้องการทำอะไร
- `target` = จุดรับหลักใน Manual
- `fields` = ข้อมูลที่งานนั้นต้องใช้

Foundation จะไม่ใส่ field เผื่ออนาคต ถ้ายังไม่มี use case จริง

ภาษาแอปต้องไม่ผูกกับหน้าจอ AI และต้องสามารถส่งเข้าเกทรับของ Manual โดยตรงในการทดสอบได้

## 5. ของเดิม: เก็บอะไร / ไม่ถือว่าอะไรต้องรอด

### เก็บไว้ก่อน เพราะมีประโยชน์ชัด

- Runtime และ business logic ที่พิสูจน์แล้ว
- Runtime session bridge ที่ทำให้หน้าเดียวกันใช้ Runtime ชุดเดียวกัน
- durable readback / validation ที่ช่วยยืนยันผลจริง
- test suite เดิมที่คุม regression

### ไม่ถือว่าต้องรอด

- Master Input UI เดิม
- Master Input router ในรูปปัจจุบัน
- Home แบบปัจจุบัน
- top navigation แบบ Store / Ride / Finance
- การจัดหน้าเดิมที่แยกตามเมืองเก่า

ตัวเหล่านี้จะถูกประเมินจากความเหมาะกับทรงใหม่ ไม่ใช่จากการที่เคยใช้งานได้

### หลักการตัด

ถ้าของเดิมทำให้โครงใหม่ต้องมี adapter หลายชั้น หรือมีข้อยกเว้นเพื่อรักษามัน ให้พิจารณาแทนที่มากกว่าปะเพิ่ม

## 6. ลำดับทำงาน

ทำ 3 track ไปพร้อมกัน แต่ทดสอบแยกกัน

### Track 1 — AI Foundation

สร้างหน้า AI ใหม่แบบขั้นต่ำ

ต้องทำได้:

- รับข้อความธรรมชาติ
- เรียก interpreter
- ส่งความหมายเข้าเกทส่งออก
- แสดงสิ่งที่เข้าใจและสิ่งที่จะส่ง

Acceptance ตัวอย่าง:

`ข้าว 65`

AI ต้องตีความได้ว่าเป็นการสร้างรายจ่ายชื่อข้าว จำนวน 65 บาท

### Track 2 — Manual Foundation

สร้าง Manual shell จากโครงเดิมโดยตัดรายละเอียดที่ยังไม่จำเป็น

ต้องทำได้:

- รับ App Language เข้าเกทรับเข้าโดยไม่ผ่าน AI ได้
- ตัวกระจายงานส่งเข้า INCOME / OUTCOME / LEDGER / CALENDAR ได้ถูก
- พื้นที่ปลายทางเรียก logic ขั้นต่ำที่เกี่ยวข้อง
- แสดงผลและ readback ที่คนอ่านเข้าใจ

Acceptance ตัวอย่าง:

ป้อน App Language ของ `ข้าว 65` โดยตรงที่เกทรับเข้า

เกทรับเข้าต้องส่งเป็น OUTCOME และ Manual ต้องแสดงรายการกับผล logic ตรง

### Track 3 — Output Gate + Input Gate Foundation

ต่อ AI output → เกทส่งออก/วุ้นแปลภาษา → App Language → เกทรับเข้า/ตัวกระจายงาน → Manual

ต้องพิสูจน์ว่า:

- วุ้นแปลคำ / หน่วย / field เป็นรูปมาตรฐานได้ตรง
- เกทส่งออกไม่ปล่อยรูปที่ผิด contract
- ข้อมูลไม่หายและความหมายไม่เปลี่ยนกลางทาง
- เกทรับเข้ากระจาย target ไปยังพื้นที่ที่ถูก
- target ไม่ถูกเปลี่ยนเอง
- คำหรือ target ที่ไม่รู้จักไม่ถูกเดา
- error ของ AI, เกทส่งออก, เกทรับเข้า และ logic ภายใน Manual แยกจากกันได้

## 7. Acceptance Slice แรก

ใช้คำสั่งเดียวก่อน:

`ข้าว 65`

เส้นทาง:

`คน → AI → เกทส่งออก[วุ้นแปลภาษา] → App Language → เกทรับเข้า[ตัวกระจายงาน] → OUTCOME → logic ภายใน Manual → readback → แสดงผล`

ผ่านเมื่อ:

1. AI เข้าใจความหมายถูก
2. เกทส่งออกแปลและปล่อย App Language ถูก
3. เกทรับเข้ารับและกระจายเข้า OUTCOME ถูก
4. ไม่มีความหมายเปลี่ยนระหว่างสองเกท
5. Logic ขั้นต่ำใน Manual วิ่งถูก
6. ผลที่แสดงตรงกับสิ่งที่เกิดขึ้น

Foundation test ไม่จำเป็นต้องเขียนข้อมูล production จริง การทดสอบ logic สามารถใช้ isolated/test state แล้วอ่านกลับผลเพื่อพิสูจน์ flow

## 8. UI รอบฐาน

### AI

มีเท่าที่จำเป็น:

- พื้นที่บทสนทนา
- ช่องพิมพ์
- สถานะสั้น ๆ ตอนตีความ
- preview ความหมาย / ภาษาแอปที่เกทส่งออกกำลังปล่อย

### Manual

มีเท่าที่จำเป็น:

- แถบหรือพื้นที่ INCOME / OUTCOME / LEDGER / CALENDAR
- พื้นที่รายการ/ผลหลัก
- จุด Audit ที่เห็นว่าเกทรับเข้าได้รับอะไรและกระจายไปที่ไหน
- ปุ่มที่จำเป็นต่อ vertical slice เท่านั้น

เกทส่งออกและเกทรับเข้าไม่มีหน้า UI หลักของตัวเอง ถ้าต้อง debug ให้เห็นเฉพาะ input → output / destination ที่จำเป็น

ยังไม่ตกแต่งให้ครบทุก use case

## 9. Settings

ยังไม่แตะในรอบนี้

Settings จะกลับมาหลัง AI + Manual + Output/Input Gate ผ่าน foundation แล้ว เพื่อให้ของจริงเป็นตัวบอกว่า Settings ต้องถืออะไรบ้าง

## 10. ชื่อและภาพรวม

ชื่อฐานของแอปสามารถกลับมาใช้:

**YGPH — Yggdrasil Personal Helper**

METROPOLIS ยังเป็นชื่อโลก/ประวัติของระบบได้ แต่ไม่บังคับให้รูปหน้าใหม่ต้องเดินตามการแบ่งเมืองเดิม

## 11. สิ่งที่ตั้งใจไม่ทำในรอบนี้

- ไม่ rewrite business logic ทั้งหมด
- ไม่ขยาย AI ให้รองรับทุกคำสั่ง
- ไม่ทำ Dashboard เต็ม
- ไม่ทำ Settings ใหม่
- ไม่ทำทุกปุ่มของ Manual
- ไม่สร้างเกทให้กลายเป็น business engine
- ไม่ออกแบบ feature เผื่ออนาคตโดยไม่มี Reality รองรับ
- ไม่เปลี่ยน production current pointer จนกว่าจะมี device acceptance

## 12. ตัวเลือกที่พิจารณา

### ทาง A — ปะ Master Input เดิมเข้ากับหน้าปัจจุบัน

เร็วสุด แต่มีแนวโน้มลากโครงเก่าและความซ้ำต่อไป

**ไม่แนะนำ**

### ทาง B — สร้าง AI ใหม่ + เกทส่งออกที่มีวุ้นแปลภาษา + เกทรับเข้าที่มีตัวกระจายงาน + ลด Manual เหลือฐาน + ใช้ logic เดิมที่ยังเหมาะ

เปลี่ยน surface และรอยต่อให้ตรงกับ Reality ใหม่ แต่ยังใช้เครื่องยนต์ที่พิสูจน์แล้วเมื่อมันช่วยจริง

**แนะนำ / APPROVED**

### ทาง C — Rewrite ทั้งแอป

สะอาดที่สุดบนกระดาษ แต่เสี่ยงทิ้ง business logic และบทเรียนที่ยังมีค่าเกินจำเป็น

**ยังไม่ควรทำ**

## 13. Stop Condition ของ Foundation

หยุดเพิ่มของเมื่อ vertical slice แรกผ่านครบ

หลังจากนั้นค่อยประเมิน Reality ใหม่ แล้วเปิด Full House Phase สำหรับ AI และ Manual ทีละส่วน
